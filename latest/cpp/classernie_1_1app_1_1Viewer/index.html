Detailed Description

The viewer keeps no scene state of its own: panels read the scene each frame and write edits back through Scene::Set, so edits from code and from the GUI are one history, seen by both. What only the GUI needs (its cameras, the viewport's render product, lighting presets) is defined under SessionRoot(), which panels hide unless asked to show it.

The viewer defines its own perspective camera on opening, framing the scene (PerspectiveCamera(), the default view). The viewport looks through it or any Camera prim of the scene; navigating moves whichever camera it looks through.

Drive it in one of two ways, both on the thread that created it (GLFW needs the main thread on macOS): * Run() loops until the window closes; * Step() draws one frame and returns, for callers that own the loop, such as a simulation.

Each frame runs, in order: OnFrame callbacks; the UI, whose panels may edit the scene, then OnUi callbacks; OnPreRender callbacks; the scene's sync and render, and presentation; OnPostRender callbacks. Callbacks run on the viewer's thread; an exception from one ends that frame and propagates out of Step or Run, and the viewer can step again afterwards.

Applications extend it with panels (AddPanel), menu items (AddMenuItem) and callbacks; TerrainGen's viewer is one such application, adding its terrain configuration panels.
